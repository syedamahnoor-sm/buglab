The assembly layer would:

**Eligibility and ranking would follow these rules.**

1. **Filter before scoring.** Require published, playable, supported challenges. Reject unknown IDs, unavailable entries, drafts, archived challenges, and reserved unsupported completion modes.

2. **Exclude known verified completions from new work.** Historical completion versions still exclude the challenge. A changed version does not silently make it unfinished again.

3. **Suppress browser-observed solves from new-work suggestions by default**, separately from verified exclusions. Explain that suppression as “solved in this browser.” Such records never increase verified counts.

4. **Respect hard learner choices.** Do not silently override an explicit difficulty constraint. Treat estimated time as a soft preference unless a strict filter is deliberately introduced.

5. **Score eligible candidates with bounded integer factors:**

   | Factor | Maximum | Meaning |
   |---|---:|---|
   | Difficulty fit | 30 | Fits the chosen or conservative starting level |
   | Explicit goal match | 20 | Matches the learner’s selected category |
   | Practice request | 20 | Related to a locally recorded “need practice” response |
   | Coverage opportunity | 15 | Adds practice in an area underrepresented in the selected evidence source |
   | Continuity | 10 | Related public topics/category from an actual recent completion or local observation |
   | Time fit | 5 | Catalog estimate fits the selected budget |

   Missing evidence contributes nothing; weights are not renormalized into a misleading confidence percentage. Featured status would not override learner fit.

6. **Resolve ties consistently:** score descending, challenge number numerically, then ID. No randomness, ambient clock, network ordering, or hidden state.

When verified history is unavailable, the engine cannot guarantee that a candidate has never been completed elsewhere. The UI must say **“Suggested challenges—verified history unavailable”**, rather than claiming those challenges are definitely unsolved.

**Cold-start and sparse-data behavior would remain conservative.**

For a new learner, use beginner challenges, category variety, and shorter catalog estimates. Without a preference, Challenge 002 is a defensible first candidate under catalog-order tie-breaking; the intermediate featured Challenge 001 should not automatically win.

Difficulty adaptation should initially distinguish **difficulty preference and exposure** from measured ability:

- Default to beginner; respect an explicit learner choice.
- Offer an optional stretch rather than forcing a promotion.
- Never demote someone because records are missing or because they requested recall practice.
- Do not calculate success rates from browser solves, repeated solves, or absent attempts.
- Gate evidence-based automatic progression on trusted, version-compatible data.

A proposed future threshold is three distinct verified completions at the current tier before suggesting the next tier. That is a product heuristic requiring approval—not a proficiency finding. Historical difficulty cannot safely be inferred from today’s catalog label alone.

For skill gaps, V1 should use the existing six categories as **practice coverage areas**. Public tags can explain relatedness. Neither completion counts nor unobserved categories justify “weak skill,” “mastered,” or percentage proficiency labels.

Suitable copy includes:

- “You asked for more practice with this topic.”
- “This category is not represented in your saved browser record.”
- “A beginner investigation matching your selected focus.”

**Recall and learning paths need separate ordering rules.**

Recall recommendations should reuse [the existing scheduler](<C:/Users/Laptop Zone by JK/buglab/src/lib/learning/schedule.ts:39>):

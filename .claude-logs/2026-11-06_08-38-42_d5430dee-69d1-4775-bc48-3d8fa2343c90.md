# BugLab Frontend/Backend Integration Readiness Report

**Scope:** I only read files. Nothing in the repo was written, nothing in git was changed, and I didn't start a server or contact the other session. Sprint 13's `src/lib/progress/calendar.ts` is untracked and still changing, so what I say about streaks reflects the current working tree.

## 1. Where the frontend and backend data models don't match

| # | Frontend (`src/lib/learning`, `src/lib/progress`) | Backend (`src/server/session`) | Effect |
|---|---|---|---|
| 1 | `ObservedSolve` has `firstSolvedAt`, `lastSolvedAt`, `timesSolved` and `source:"browser"`. Re-solving updates it. | A completion happens once per session and is permanent (`completedAt`). A replay records nothing new, and a completed challenge cannot be started again. | The server can never supply `lastSolvedAt` or `timesSolved`. The "solved-again" activity event, and practice `applied` (`solve.lastSolvedAt > openedAt`), would stop working on server data. |
| 2 | One record holds every challenge. | Data is per challenge (`GET /api/challenges/:id/session`). Nothing lists a learner's completions, as `progress/source.ts` already notes. | Progress would need one call per published challenge. A list endpoint is required. |
| 3 | No expiry. The record is kept indefinitely. | Learner idle expiry is 30 days, absolute expiry 90 days (`expiry.ts`, marked "provisional OD-7"). An expired learner is never revived. | Verified history and any server-side Journal would be erased at 90 days at the latest. Longest streak and the activity timeline would reset. |
| 4 | Local calendar days (`LocalDay`, `days.ts`). Recall due dates and streaks are computed in the browser's time zone. | ISO 8601 UTC instants only. | Compatible only if the server sends instants and the client works out the days. Streaks and due dates must not be computed on the server without a time-zone decision. |
| 5 | A reflection requires `record.solves[id]` (a browser solve). | Nothing on the server knows about reflections. | Decide whether a server reflection requires a verified completion. If it does, existing reflections for browser-only solves can't be migrated as they are. |
| 6 | Completion is keyed by challenge ID only. | Sessions carry a `contentVersion`. An unfinished session restarts when the challenge changes, and a completed one keeps its old version. | Fine for "solved", but `restarted: true` has to clear workspace state (§11.2 of the foundation doc). That state is not the learning record. |
| 7 | `SolveRecorder` records a solve for every `correct` response object. | Under the session handler, a replay with the same `Idempotency-Key` returns `correct` again. | A replay would add a browser solve again. Harmless now, but `timesSolved` would be inflated. |
| 8 | The live diagnosis route uses `restrictToPublished(...)`. | `app-services.ts` passes `challenges.diagnosisRegistry` without the publication gate. | **Real gap:** once mounted, draft or archived challenges with answer keys could be started and completed. This must be fixed before mounting. |
| 9 | The session client expects a 1 KiB body cap on session writes (`handlers.ts`). | n/a | Reflection payloads can reach about 2.7 KB (4 × 600 + 280 characters), so they need their own handler and cap. |

## 2. Required API endpoints

**Already designed** (handler factories exist, the client in `api.ts` already calls them, but nothing is mounted):
- `GET` and `POST /api/learner`
- `GET` and `POST /api/challenges/:id/session`
- `GET /api/challenges/:id/attempts`
- `POST /api/challenges/:id/diagnosis` with `Idempotency-Key` (`diagnosis-handler.ts`, behind `getAppServices().diagnosis`)

**Missing, needed for Progress:**
- `GET /api/learner/completions` returns `[{ challengeId, completedAt, contentVersion }]`. It should include only completed, non-superseded sessions for published challenges, not the `completion` payload (the resolution text should stay per challenge), and use `no-store` and `Vary: Cookie`. This is the only server read Progress needs at first.

**Missing, needed for Journal and reflections (later phase, needs decisions):**
- `GET /api/learner/reflections`
- `PUT /api/learner/reflections/:challengeId`, which is idempotent and upserts. It should carry `updatedAt` or an `If-Match` version for conflict detection.
- `DELETE /api/learner/reflections/:challengeId`
- `POST /api/learner/reflections:import`, a one-time bulk migration that is idempotent per challenge ID and requires explicit consent.
- `GET /api/learner/export` and `DELETE /api/learner` (data rights) once text is stored on the server.

**Not needed yet:** endpoints for recall, practice or activity (see §5).

## 3. Anonymous cookie and session requirements

- The `buglab_learner` cookie is `HttpOnly; SameSite=Strict; Path=/api`. JavaScript can't see whether it exists, and server-rendered pages at `/progress` and `/journal` never receive it. All learner reads therefore have to be client-side fetches to `/api/*`. `GET /api/learner` is the only way to tell `none`, `expired` and `active` apart.
- Writes must send a JSON content type and pass the strict same-origin policy. Requests with no `Origin` header are allowed only with `Sec-Fetch-Site: same-origin`. **`BUGLAB_APP_ORIGIN` must be set in every deployment**, otherwise all writes fail behind a TLS proxy.
- Progress and Journal should only read: `GET /api/learner`, then completions. Creating a learner should stay a challenge-workspace action through `createSessionCoordinator`. Otherwise every dashboard visit creates a learner, and learner creation has no rate limit yet (§10 of the foundation doc).
- During the cutover, the old `buglab_attempt` cookie and the `wrongAttempts` limiter coexist with the new ones until the live diagnosis route is swapped. Both should be retired in that same step.
- A 401 or expired learner during a Progress read should mean "no verified progress", not an error. Browser data still shows.
- Accounts are a separate track. `learner-link.ts` only joins an anonymous learner to an account with explicit consent and never merges automatically. Anonymous integration doesn't depend on it.

## 4. Safe migration of existing browser learning records

1. **Never upload browser solves as completions.** They are editable observations (`ObservedSolve` says so explicitly), and the backend accepts no client-supplied completion. Keep them, labelled "completed in this browser".
2. **Two origins, merged only for display.** Extend `ProgressOrigin` to `"browser" | "server"` (`source.ts`). Show a challenge as verified only when the server lists it. Show browser-only solves separately, or flagged as unverified. The selectors read a merged source, and `learning.v2` stays exactly as it is.
3. **Make no change to the local schema at the first step.** `buglab.learning.v2`, `buglab.journal.v1` and the recovery keys stay untouched. Server data is fetched and never written into localStorage, which keeps the existing guarantee that learner text is never lost.
4. **Reflections, later and opt-in.** Offer to upload them with consent, using the idempotent import. Run `exportData()` first as a backup and keep the local copy until the server confirms. On conflict, pick a documented rule (for example, the newer `updatedAt` wins and the other version goes into a recovery copy). The local record stays the source of truth until a decided cutover.
5. **Expiry safety.** As long as the server can lose a learner (90-day absolute expiry, in-memory store), the browser record must stay the durable copy. Don't delete local data just because a sync succeeded.

## 5. Data that should stay browser-local initially

- **Recall schedule and history:** `stage`, `dueOn`, `lastReviewedOn`, `stageBefore` and `attempts[]`. It is self-reported, uses local days, and contains no secrets.
- **Practice links** (`practice[]`), and the derived suggested, opened and applied status.
- **Reflection text itself** until the retention, expiry and consent decisions in §6 are made.
- **Observed solves**, kept as the browser origin indefinitely.
- **The legacy v1 journal, recovery copies and export.**
- **Derived data:** activity timeline, calendar and streaks, overview, skills. These are computed on the client and never stored.

# BUGLAB — AUTHENTICATION, IDENTITY & ACCOUNT EXPERIENCE

## Final Architecture + Design + Implementation Sprint

You are the lead frontend and authentication-integration engineer for BugLab.

Your assignment is to deliver a complete, production-quality authentication and account experience that integrates cleanly with BugLab's existing learning platform.

This is not a prototype or a collection of attractive but disconnected screens.

We want a cohesive, secure, accessible, responsive implementation with a stable architecture, reusable components, clear backend contracts, and no unnecessary future redesign.

Read the entire specification before making changes.

---

# 1. PRODUCT VISION

BugLab is an interactive debugging learning platform.

Learners investigate bugs, examine evidence, submit diagnoses, reflect on mistakes, review concepts, track progress, and receive personalized challenge recommendations.

Authentication should make the experience more valuable without becoming a barrier to learning.

The fundamental product principle is:

**Explore freely. Learn anonymously. Create an account when you want persistent, cross-device progress.**

A user must not be forced to register before exploring or solving a public challenge.

Account creation should feel like a natural upgrade to the learning experience.

# 2. CONFIRMED PRODUCT DECISIONS

Implement the following product direction:

- Anonymous challenge exploration and solving remain available.
- Registered users can sign in with email/password or Google.
- Email verification is required for email/password accounts.
- Password recovery/reset is supported.
- Account sessions are secure and persistent.
- Users can sign out.
- Account creation is optional.
- Existing anonymous learner history can be linked with explicit consent.
- Account and anonymous learner identities remain separate.
- Browser-local solves never become server-verified completions.
- Existing verified progress is preserved during successful linking.
- No automatic merging of two learner identities.
- No automatic linking of accounts solely because email addresses match.
- Initial supported roles are learner and admin.
- Registration always assigns learner; admin is never self-selected.
- Organizer is not a current backend role and must not be introduced in this sprint.
- Existing Journal, Progress, recall, and recommendation features must be preserved.

Do not change these product decisions without identifying a genuine technical or security blocker.

# 5. IDENTITY MODEL — NON-NEGOTIABLE

BugLab has two distinct identities.

A. Anonymous learner identity

- Uses the existing buglab_learner cookie.
- Identifies an anonymous learner's server-side sessions.
- Is not an authenticated account session.
- Uses the existing opaque-token and server-side hash design.
- Must not be replaced by a browser-supplied learner ID.

B. Registered account identity

- Is issued and verified by the selected authentication provider.
- Uses a separate secure account session.
- Has a stable provider account ID.
- Is not equivalent to the anonymous learner ID.

Account-to-learner linking is the only approved relationship between these identities.

Do not:

- Treat the anonymous cookie as a login credential.
- Derive account ownership from localStorage.
- Trust account IDs or learner IDs supplied in request bodies.
- Copy browser-local completion flags into verified completion records.
- Automatically merge anonymous and registered learner histories.
- Link accounts based solely on matching email addresses.

After a successful account link, the backend must resolve the same learner through the authenticated account.

Existing verified challenge sessions, attempts and reflections remain associated with that learner.
